¶ HexOS documentation style guide

Use this guide when writing or updating HexOS documentation. A reader should be able to follow the steps without already knowing the feature.

¶ Language

Use short sentences and familiar words. Explain a technical term when the reader first needs it. Write in American English: organize, color and behavior.

Avoid metaphors, idioms and cultural references. Write “HexOS runs on top of TrueNAS.” Describe results directly, such as “Your files appear.”

¶ Page structure

Give each page one clear purpose. Start with what the reader will accomplish, followed by anything they need before starting. For a procedure, include the starting screen, the exact controls, the expected result and how to check that it worked.

Use the same text for the page title and its first heading. Write a short description explaining what the page helps the reader do. The description appears below the title.

Use sentence case for headings. Capitalize the first word and proper names, including feature names such as Buddy Backups, Command Deck and Activity Center. Write HexOS and TrueNAS exactly this way.

Keep existing page addresses when updating a guide so that links to it continue to work. Link to other documentation with a page path, such as /features/folders, without .md.

¶ Referring to the interface

Quote each control's wording and capitalization exactly, in bold. For example: Click Continue.

For navigation, put each item in bold with a plain > between them: Settings > Notifications.

Use click for buttons and menu items. Use screen, menu, card, tile, info panel, button, dialog and tab consistently. A card displays information; a button performs an action. A tab changes the visible section. Use “press” when describing a keyboard key, such as Escape.

Write an instruction before its screenshot. Explain what appears after the action. Do not use a screenshot as a substitute for the instruction.

Use inline code for values and short commands. Use a fenced code block for a longer example. State whether an example is complete or is a fragment to add to another file. Test commands before giving them to readers, and explain any value they need to replace.

¶ Callouts

Use a callout for a risk, prerequisite or useful note. Start with a bold lead word and put its class on the next line:

> **Warning:** Keep the original files until you have checked the restored copy.
{.is-warning}

Warning: Keep the original files until you have checked the restored copy.

Lead word Class When to use it
Danger: {.is-danger} An action can erase data or cause another critical outcome.
Warning: {.is-warning} A risk or a common mistake needs attention before continuing.
Requirement: {.is-success} Something must be ready before the next step.
Info: {.is-info} Context helps the reader understand the step.
Tip: {.is-tip} A short suggestion makes the task easier.
Help: {.is-troubleshooting} The reader needs a troubleshooting guide or a way to ask for help.
Thank you: {.is-contribute} Credit community authors at the top of their guide.

Keep community attribution when revising a page. Do not add a Contribute footer to a new guide. Existing credits should remain with the guide.

¶ Screenshots

Show each action with a screenshot of the matching screen. Take screenshots on a desktop in light mode. Include enough surrounding interface, such as the sidebar and the screen behind a dialog, to help the reader find the control.

Before capturing a screen, wait for loading and animations to finish. Check that the intended tab, menu or dialog is open. Close unrelated overlays and remove development controls. Keep text readable and leave important controls inside the frame.

¶ Protect private information

Never include passwords, recovery keys, API keys, paid access tokens, personal photographs or private customer information. Use a test account and non-sensitive sample files. Use your own media or media you have permission to share. A test image can illustrate a screen, but it does not prove that an operation succeeded.

¶ Names and folders

Store images in a folder named for the guide. Use lowercase names with hyphens, such as create-a-new-folder/encryption-options.png. Avoid spaces and names such as screenshot3.png.

Write alt text that describes the useful content of the image. The filename can be a starting point, but a screen reader needs a meaningful description.

¶ Screenshot markup

Put exactly one image in each screenshot dropdown, with a short caption in its summary. Leave a blank line after </summary>:

<details>
<summary> New folder button </summary>

![New folder button on the Folders screen](/create-a-new-folder/new-folder-button.png){.medium .framed}
</details>

The current site displays this simple pattern as an inline figure with a caption and click-to-enlarge. Extra text or a second image inside the dropdown prevents that conversion. Put explanations outside the dropdown and give each screenshot its own caption.

Use {.medium .framed} after the image. Keep all classes in one pair of braces. Do not write {.medium}{.framed}.

Class Width limit in the standard image markup
.small 320 pixels
.medium 560 pixels
.large 800 pixels
.framed Adds a border, rounded corners and a shadow

The current site's inline-figure layout controls its own display size. Keep the classes so the source also works with the standard renderer.

¶ Check the finished page

Open the saved page and check every screenshot at its displayed size and enlarged. Confirm that it loads, matches the instruction, shows the current interface and contains no private information. Check captions and alt text too. A successful file upload alone is not enough.

¶ Verify the instructions

Follow the complete procedure on a test server using the software version described. Check the final result, not only that a button can be clicked. Verify warnings, limits and alternative paths against the implementation or a relevant test. Keep a record of what was tested and what still needs verification.

Ask another reviewer to follow the written steps. Check every link and resolve missing screenshots before asking for publication. Keep an old version in the review archive when replacing a guide; do not leave contradictory instructions in the active page.
